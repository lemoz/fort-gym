# Astra standard-input endurance v1

Prepared, not launched. This is a separate exploratory campaign after all six
frozen selected-workshop v2 attempts have retained actual outcomes. It is not a
seventh matched trial, a continuation of a selected winning fort, or evidence
that standard input beats shortcuts. The active cohort is unchanged.

## What we are testing

Can Astra Medium grow and manage a fortress through one full elapsed game year
and beyond using the ordinary keyboard interface, readable 120-by-40 screen,
and its own retained memory? The candidate includes the exact workshop job-menu
clock-feedback correction and checkpoint-bound portable budget extensions.
Those runtime changes distinguish this campaign from the frozen controls study.

The condition preserves the standard-input model, prompt, bindings, observation,
clock bound and transport. Only the condition identity and initial cumulative
budgets differ from the standard-input study file. No workshop-job shorthand,
structured private evaluation data, suggested gameplay strategy, injected keys
or human rescue is added. The seed receipt is the same original fresh seed;
model memory and usage start empty once, at the start of this campaign.

## Continuous play with bounded windows

The first four responses exercise a real native save boundary. That is not a
successful fortress, a meaningful performance score, or the campaign endpoint.
After auditing that save and its owner's teardown, append cumulative ceilings
of 1,028 responses and 40,000,000 returned tokens at the exact checkpoint.
The initial token ceiling is 500,000, not a reservation or expected expenditure.

Resume the same fort in windows of at most 64 further responses. Later windows
inherit the recorded extension instead of appending it repeatedly. Preserve
original condition bytes, memory, usage, prompts and full trace/journal history.
No window is a new independent trial. A later budget increase must be another
recorded checkpoint-bound append, not an accounting reset.

The offline planner verifies the completed previous owner, native save chain,
condition, source/image, resource limits and inherited budget. It discovers
the actual final checkpoint, caps the final window at remaining dispatches,
and writes only a new declaration outside original evidence. It refuses
unfinished owners or source/image/resource migrations. It neither starts a
game nor establishes current VM teardown or fresh account admission.

Example after an actual completed window, using resolved absolute paths:

```sh
python -m scripts.prepare_keyboard_endurance_window \
  --previous-attempt /absolute/previous-owner-output \
  --previous-origin /absolute/previous-original-snapshot-or-checkpoint \
  --runtime /absolute/verified-runtime.json \
  --max-dispatches 1028 --max-total-tokens 40000000 \
  --steps 64 --output /absolute/new-window.json
```

The output identifies the unchanged condition and checkpoint for the existing
portable owner. Before launching, independently check the single existing local
VM is available, prior teardown is settled, the expected external evidence volume
is mounted, and the actual image matches the reviewed candidate. Keep the same
resource limits and mandatory teardown. Do not create a cloud VM, build into the
active study runtime, consume a reset, buy credits or use a paid API fallback.
Fresh subscription admission remains required before every model invocation.
All work stays within the existing spending bounds; these token ceilings do not
create new monetary authorization. Report actual returned usage and leave
unreported subscription charges null rather than claiming zero.

## Evidence and success

The first anniversary requires at least 403,200 elapsed ticks from the original
seed, not a calendar-year rollover. It is a milestone, not an automatic stop.
The response/tick ceilings provide room to reach it but do not guarantee the
model will advance time or maintain a functioning fort. A budget-limited pause,
infrastructure failure, gameplay collapse and successful autonomous continuation
must remain distinct outcomes. Never turn an incomplete owner into a verified
checkpoint or discard unsuccessful actions.

Track native elapsed time, living/dead population, useful completed buildings,
food/drink inventories, adaptation, accepted/rejected controls, returned tokens
and any reported charges. Sustained functioning needs native gameplay evidence
of replenishment and ongoing survival, not just a positive stock snapshot, queued
orders, a save reload or passing tests. The current food reader measures inventory,
not production/consumption flows, accessibility or completed workshop products;
retain those unknowns and do not claim indefinite self-sufficiency.

Audit and publish actual windows as they finish. The existing auditor accepts
at most 16 windows per report and the viewer at most 1,024 frames per recording;
use consecutive bounded recording batches with
the same campaign identity and saved cursors if the campaign spans more than
one batch. Preserve every earlier recording and make the boundaries explicit.
Website delivery is separate from source/CI acceptance. This one Astra campaign
does not establish a cross-model ranking or replace matched repeated runs.

## Remaining gates

Offline validation passed the complete functional suite with 5,749 tests and
ten skips. The final focused suite passed 135 tests after formatting, including
generated-window consumption across Astra, Sol and Terra configurations with
fake model/game/container receipts. Those checks do not constitute native
gameplay or cross-model performance results. Repository lint/type diagnostics
match the unchanged parent baseline; exact-head hosted CI remains separate.

Review and exact-head CI, an actual candidate image/runtime binding, real native
budget-extension acceptance, longer gameplay and public recording delivery all
remain required. No image digest, new native result or Year-Two success is
invented by these files. Source/image migration of the old controls saves is
not supported; beginning this fresh declared campaign avoids that transition.
