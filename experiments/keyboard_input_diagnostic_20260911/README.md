# Native keyboard menu diagnostic

The provider-free September 11 experiment used four fresh copies of Astra
attempt 1's audited decision-256 save. Each started paused at year30 tick152201.
The operator selected the same completed carpenter workshop and opened its
AddJob menu. This setup is not autonomous navigation, and no edited copy can
be resumed as a scored model campaign.

| Input through the unchanged native_keyboard/v2 executor | Native outcome |
| --- | --- |
| CUSTOM_B | Accepted; no new job; AddJob menu unchanged |
| STRING_A098 (literal b) | Accepted; no new job; AddJob menu unchanged |
| HOTKEY_CARPENTER_BED | New ConstructBed job; moved to the Job view |
| STANDARDSCROLL_DOWN, SELECT | New MakeShield job; moved to the Job view |

This is a concrete event-contract mismatch: the screen's printed `b` hotkey is
not interchangeable with either of the two generic `b` events in this menu.
The harness delivered the chosen event, but acceptance alone did not establish
a game effect. The native command and navigation controls establish that this
workshop could queue jobs without adding orders directly through DFHack.

The prepared literal-character-reference profile therefore does not address
this measured case. It remains unlaunched and unchanged, not validated for a
model trial by this result. Next, make the standard-input contract faithfully
represent the game's visible key bindings, validate that mapping natively, and
declare any model test as a separate condition. Do not add a strategy, choose
the model's job, automatically retry its input, or relabel earlier results.

## Acceptance qualifications

The original full-frame assertion failed after all four arms completed.
The native starting menu, selected building, calendar and queue were identical.
A separate, explicitly post-hoc review found the complete workshop sidebar's
glyphs and colors identical; one to three changing map glyphs lay outside it.
The original failure, exit code1 and changed coordinates are retained in the
[versioned result](../evidence/keyboard_input_native_diagnostic_20260911.json).
The post-hoc review is not a retroactive pass of the original criterion.

The first attempt completed only CUSTOM_B, then failed the second game's port
bind check. It was retained. The second attempt changed only local per-arm
ports to 5589..5592, with one game at a time. Its native fixture and Lua probe
are published here byte-for-byte as executed. They target the frozen image/source
and mounted `/previous-evidence/astra/segment-1/checkpoint`; the operator provided
a fresh writable evidence volume and copied these files read-only into /launch.

All game processes and both VM attempts were shut down. No model call, game
tick advancement, native save, new scored checkpoint, cloud VM or public
deployment occurred. Source-checkpoint inventory verification passed after
execution. Hardware and energy cost is unmeasured, not asserted to be zero.
No model improvement, job completion, sustainability or general keyboard
equivalence follows from these input-level results.

The UI setup uses documented [DFHack 0.47.05-r8 GUI operations](https://docs.dfhack.org/en/0.47.05-r8/docs/dev/Lua%20API.html#fortress-mode)
to position the disposable copy's cursor. Tested inputs still go through the
unaltered native keyboard executor; the probe only reads the resulting queue.
