## Follow-up repair and continuation boundary

`observe_container_output` now supports an explicit maximum of three attempts for
only the literal exchange listing and request-file readiness probes. Each failure
must first be retained privately with the fresh container state, bounded command
output, full-output digest and attempt number. Only an identified, healthy running
container permits another read. Unknown state, an exited container, exhausted
attempts or inability to retain the diagnostic stops that retry path. Default
callers still use one attempt.

This never retries a model call, game key, response publication, unknown shell
command or another container. The new path has unit coverage but has not yet run
in a new native window. The historical window-v operator remains unchanged. A
new owner must opt in with unique diagnostic receipts, preserve all current usage
and unknown losses, and use shorter checkpoint segments before another gameplay
run. No continuation from the unsaved 12,724 ticks is claimed.
