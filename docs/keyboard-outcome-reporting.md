# Native keyboard performance reporting

The general descriptive campaign profile recognizes `KEYSTROKE` alongside the
existing structured action types. Its execution result remains independently
accepted, rejected or unknown. Recognizing an input type does not award completed
work, successful adaptation, survival or autonomous-fortress credit.

A read-only replay of audited checkpoint 375 reproduced the earlier bug: all
375 retained rows appeared under action type `UNKNOWN`, although their native
type was `KEYSTROKE`. With the repair those same rows appear under `KEYSTROKE`,
with unchanged 374 accepted and one rejected result. Every metric, 77,000 retained
elapsed ticks, cumulative usage, loss history and success verdict stayed identical.
This canonical trace is distinct from the 391 accounted model responses, which
also include the historical lost branch. Do not sum ancestor traces or drop usage.

Resource explanations now describe the provenance checks actually used by the
metric reader: unverified UI estimates stay unknown, while known native counts
are not production or consumption measurements. A screen-only initial observation
does not supply a private fortress baseline. Missing baseline metrics stay unknown;
the reporter neither parses screen text as native stock evidence nor feeds private
evaluation results back to the playing model.

Focused profile validation passed 50 tests, with scoped Ruff and mypy passing.
The source-bound before/after reports and trace remain private. This evaluation
repair was developed in a separate checkout while window k ran on frozen source
`7416f65b2`; it changes neither that live experiment nor its model inputs. This is
reporting proof, not production website delivery or an independent model trial.

## Optional measured food inventory on the campaign page

The continuation API supports a separate
`fortgym.keyboard-food-inventory-outcome/v1` aggregate. A publication must declare
`fortgym.campaign-food-measurement/v1`, retain independent private-review and
screen-only-model-input evidence, and bind its initial reading to the parent
checkpoint. Complete plus unknown readings must cover the initial observation
and every new decision boundary. Endpoint units are nonnegative safe integers
from complete readings or explicit `null`; a partial sum cannot become a total.

The existing `outcome_counts.food_stock: null` remains unchanged. New inventory
coverage is separate from historical unknowns, the UI estimate, accessibility,
production, consumption and sustainability. The API only exposes authored
aggregate fields; it drops extra item records and raw errors.

The existing campaign page displays initial/final native-predicate food units
and complete/unknown reading coverage. Unknown and measured zero are distinct.
Synthetic API and Node rendering fixtures exercise those cases and historical
compatibility. No fixture is a completed native-run publication, and no running
window is added to the completed-results allowlist. This update is prepared in
an isolated worktree while window n runs on frozen source `567251e7414795d52c87e1450eca146bfb419069`.
Browser visual acceptance, audited window-n publication and deployment remain
separate work.
